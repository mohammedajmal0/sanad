How this guide is written

This guide uses the writing rules of ASD-STE100, Simplified Technical English (STE).

  • An instruction has 20 words or fewer.
  • A description has 25 words or fewer.
  • A paragraph has 6 sentences or fewer.
  • Each paragraph has one topic.
  • Verbs are active and in simple tenses.
  • Each word has one meaning in this guide.

Technical names and code names stay as they are, for example gold.invoice_issues or recall@5. We did not check each word against the official STE dictionary, so some words can be outside its approved list.

The phase files in docs/learning-log/ stay the source. This guide is a snapshot of 11 November 2026.

Twelve lessons

The same lessons came back in many phases. Each lesson below has one rule, the reason for the rule and the places where it occurred. Learn these first. They answer most "why" questions in an interview.

L1

Not everything is an agent

Use an agent only when the work needs tool choice and actions. Use retrieval, a workflow or a model for the other work.

An agent costs more, is slower and is harder to test. In Sanad, only billing and service-desk triage need tool choice plus actions.

  • P0 Delivery analytics is NL-to-SQL retrieval (a Genie agent). Invoice capture is a workflow. Forecasting is a model.
  • P4 The brief said "similar-ticket search". A count of tickets per day against a normal day found the incident better.
L2

Plant the answers before you test

Put known problems into the data on purpose. Then each test has a fixed right answer.

Without a fixed answer, a confident reply and a correct reply look the same.

  • P1 Seed 42 and three planted problems, each with a cause (one carrier in one region), not only a symptom.
  • P3 Retrieval ground truth is the right document plus a short exact phrase. It stays valid when the chunks change.
  • P6 The 34 evaluation cases take their expectations from the planted data and the policy text.
L3

The agent never sees more than the person who asks

Run each data tool with the identity of the user. Set each permission in trusted code, never in a parameter that the model fills.

Then the Phase 2 rules apply to the agent with no change, and the model cannot make its own access wider.

  • P2 Three locks: a grant, a row filter and a column mask.
  • P4 auth = "user" (ADR 0004). The audience comes from is_account_group_member() inside SQL. The model chooses what to look up, never who asks.
  • P4 Memory holds no tool data, because memory is outside Unity Catalog permissions.
  • P4 Service Desk hid an IT-only article from a user outside it_support. This was governance, not a model mistake.
L4

Put each rule where nobody can skip it

Put a business rule in the tool code or in the system of record. Do not keep it only in the prompt.

The model fills the arguments. A rule in a prompt is a request. A rule in code is a check.

  • P4 The write tools check their arguments. The answer schema says "no citations means low confidence".
  • P5 The mock ERP applies the approval tiers. There is no "manager approved" flag, because the model could fill it in.
  • P5 Take the rule from the source policy, not from a summary of it.
L5

The model labels; code speaks

Let the model make each judgement as a choice from a closed list. Let code write each part that must be exact: citations, IDs, statuses and fixed replies.

The model copies badly and changes the words of "reply with exactly this". It fills a closed list (an enum) reliably.

  • P4 One extra call with no tools makes the Answer JSON. Code carries the citations of the specialists and of each record that the answer names.
  • P4 Code changes a non-breaking hyphen in an ID to a plain hyphen.
  • P6 Improvement #5: the labels out_of_scope and decline_memory select a fixed sentence in code.
L6

Measure the measurement

Before you trust a strange number, find out how the number was made.

In Sanad, many numbers were wrong because of the count, not because of the system.

  • P1 The event log without a flow filter said that each table "wrote 2,000 rows".
  • P6 Tokens per question: the first count said 218,617. The correct count was 8,759.
  • P6 The grounded judge cut tool output at 4,000 characters and graded without the data.
  • P7 Telemetry failed with only a WARNING, so production traces had no spans. Monitor the monitoring.
L7

Read each failure. One run is a sample of one.

Read the failed cases one by one. Run a gate more than one time before you trust it.

An average hides different causes, and each cause needs a different fix.

  • P3 recall@5 differed on only 3 questions (p = 0.25). The ranks differed on 9 of 10 (p = 0.02).
  • P4 Gate A passed on 8 Nov. On 9 Nov the same prompt passed 1 of 3.
  • P6 Each 0.9x score hid a different story: a routing gap, an amount from the user, a judge error.
L8

A prompt change moves behaviour to other cases

After each prompt change, run the full evaluation set again. If a rewrite fails, go back to the last good version.

With a small model and twelve rules, each edit changes answers in other cases.

  • P6 Improvement #2 raised tool choice to 1.0 and dropped "follows guidelines" to 0.60.
  • P6 Rule 6 had two rewrites and caused three regressions. The return to its baseline text passed.
  • P3 A fair test changes one thing only.
L9

Deny by default

Block everything, then allow the items that you know are safe. Do not keep a list of the dangerous items.

A list of writes is safe only until somebody forgets to update it.

  • P5 approval_rules gates each MCP tool except reads (get_*).
  • P3 The audience filter fails closed: no departments means policies only.
  • P5 A server that is not in Databricks gets the plain MCP client and no workspace token.
L10

Fail honestly

When something fails, say exactly what you know. Never say more.

"Unavailable" is not "nothing happened". A calm but false message can cause a duplicate write or a wrong decision.

  • P5 A refused connection means "nothing was saved". A timeout means "it may have been saved; do not try again".
  • P6 no_false_claims fails an answer that claims a write that did not run.
  • P7 The fallback answer has the badge "not checked against the answer format". The dashboard says "not measured yet".
  • P7 Name the failure that each fallback covers. The model fallback does not cover a refusal.
  • P8 The system tour shows what is not built yet, with dashed and dotted lines.
L11

Check the source. Test the assumption.

Before you build on a fact, test it one time. Before you call a model output invented, read the sources that the model could read.

Many assumptions in Sanad were wrong. One quick test or one read of the source found each one.

  • P2 One test GRANT showed that groups-v2 create made the wrong type of group.
  • P3 A count of chunks per document (1.0) showed that ai_prep_search did not cut our documents.
  • P5 "DUP" looked invented. It is the real reason code in the credit-note policy.
L12

Isolate Beta features. Write down what you defer.

Keep Beta and preview features behind a thin layer. When you defer a fix, write its cost and its upgrade path.

Free Edition and Beta services change and refuse things. A written deferral is a decision. An unwritten deferral is a surprise later.

  • P0 ADR 0001 isolates Beta features.
  • P3 ai_prep_search lives in one CTE, and section is the measured fallback.
  • P4 runtime/ is the thin layer. The graph uses no Agent Bricks types.
  • P7 Production tracing stays simple, and the agent card records the gap and the fix.

P1.16 NovL2

Synthetic data generator with planted problems

data_gen/generate.py makes 2,000 accounts, about 4,000 contacts, 50,000 orders with invoices and shipments, and about 10,000 IT tickets for Nov 2025 to Oct 2026. CRM and ERP data are CSV files (batch exports). Tickets are JSON lines, one file for each month (an event stream).

seed_problems() plants the three problems in Sanad in one page. They are the ground truth for the evaluation. tests/test_data_gen.py checks three things: the same seed gives the same data, the row counts are correct, and each planted problem is present.

Key ideas

  • Fixed seed. random.Random(42) gives the same "random" data in each run. The right answers for the evaluation then do not move.
  • Signal and noise. The base data already has about 3% late deliveries and about 2 VPN tickets a day. A planted problem must be clearly above that background.
  • Plant a cause, not only a symptom. One carrier in one region causes the late deliveries. The agent can then answer "why", not only "where".
  • Tests first, as a specification. We wrote the three ground-truth tests before the seed code. They defined "done".
  • No Faker. Its ar_SA locale gave US-format phone numbers. Plain Python name lists gave better data and one less dependency.

P1.27 Nov

Unity Catalog, upload and the bronze layer

The CLI logs in with the OAuth profile sanad. pipelines/setup.sql makes the sanad catalog with five schemas and the volume sanad.bronze.landing. We uploaded the data files and kept October's tickets back for a streaming demo.

P1.37 Nov

Silver layer and data-quality expectations

silver.py defines six streaming tables. They change the bronze strings into real types with TRY_CAST. Each table has a "has ID" drop rule. Invoices also have two drop rules (readable amount, readable date) and two warn rules (positive amount, not in the future). There is no fail rule. A clean run passed all 50,001 invoices.

Then we broke it on purpose. break_test.csv had 5 rows: a negative amount, abc, not-a-date, a 2027 date and a missing ID. Bronze kept all 5 rows. Silver kept 2 (the warn rows). The event log showed the count for each rule.

Key ideas

  • TRY_CAST and CAST. Serverless runs ANSI SQL. There, a bad CAST stops the run. TRY_CAST gives NULL, and the expectation then decides.
  • Warn, drop or fail. Drop a row that is of no use. Warn when the row can be correct (for example, a credit note). Fail only when the full load is broken.
  • A NULL fails each rule that reads it. The abc row failed both readable_amount and positive_amount.
  • The metrics are in the event log: event_log(TABLE(sanad.silver.invoices)), field details:flow_progress.data_quality.expectations.
  • Proof of incremental reads. The metrics of the second run covered only the 5 new rows. So Auto Loader read only the new file.
  • Silver keeps business duplicates. If silver removes them, the agent loses its evidence.

Mistakes

  • None recorded.

P1.47 NovL6

Gold layer and the streaming demo

gold.py defines four materialized views: invoice_issues, delivery_sla_by_region, ticket_trends and customer_360.

Phase gate passed. invoice_issues holds exactly INV-027711 and INV-050001 (Al-Faris, 1,440.71 SAR, invoices_for_order = 2), plus the two warn rows from break_test.csv. The Q3 2026 late rate is 16.2% in Jeddah and 1.5 to 1.9% in the other regions. Red Sea Cargo is 59.3% late in Jeddah.

For the streaming demo, we uploaded October's tickets and ran the pipeline again. bronze.itsm_tickets and silver.tickets each wrote 931 rows, and the other sources did nothing. ticket_trends refreshed incrementally and showed 30 VPN tickets on Monday 19 Oct. An animated walk-through is in the Sanad Streaming Demo.

Key ideas

  • Streaming table and materialized view. A streaming table adds new rows and never reads old rows again (a diary). A materialized view keeps a stored result equal to its query over all rows (a whiteboard). spark.read gives a materialized view; spark.readStream gives a streaming table. A dataset cannot change its type in place.
  • Refresh time. The pipeline refreshes a materialized view when it runs, not when somebody queries it. Between runs, the view can be stale.
  • Where checks go. Checks across rows (duplicates) go in gold. Checks on one row go in silver expectations.
  • Window function. count("*").over(Window.partitionBy("order_id")) puts the group count on each row and keeps all rows.
  • Join fan-out. Aggregate each fact table per account before the join. If not, the totals multiply.
  • Rate denominator. Use late / delivered, not late / shipments, because in-transit shipments have no result yet. Keep counts next to rates. A roll-up is then sum(late) / sum(delivered), never avg(rate).
  • Incremental refresh. Serverless updated only the changed day × category groups (GROUP_AGGREGATE). The planning_information event tells which technique ran and why.
  • Streaming metrics. The row count of a streaming table is on the RUNNING event "Completed a streaming update", not on COMPLETED.

Mistakes

  • event_log(TABLE(x)) gives the log of the full pipeline, not only of table x. Without origin.flow_name in the filter, each table "wrote 2,000 rows". That number was from customer_360. The fix is a filter on the flow name.
  • MeMy check answer ("a streaming table would give a duplicate invoice") named the result, not the mechanism. The mechanism: a streaming table looks at each batch alone. Two invoices in different batches are never compared, so the duplicate is missed.
  • MeI thought that each query rebuilds a materialized view. The pipeline run refreshes it. Queries read the stored result, which can be stale between runs.

P1.57 Nov

The "doorbell" job (file-arrival trigger)

The job sanad_ingest in databricks.yml has one pipeline_task. It runs sanad_medallion when new files arrive anywhere under /Volumes/sanad/bronze/landing/. It replaces the planned "generator, then pipeline" job. That job would read 0 new rows in each run (ADR 0002).

Demo. We uploaded a 3-ticket file at 10:00:21. The job started itself at 10:02:24 (trigger: FILE_ARRIVAL). Bronze and silver each wrote 3 rows, and gold.ticket_trends got three rows for 2026-11-01. No second run followed, so there is no loop.

Key ideas

  • Job and trigger. The job is the to-do list (run the pipeline). The trigger decides when. A schedule is an alarm clock. File arrival is a doorbell.
  • Two separate decisions. The doorbell decides when to run. The Auto Loader checkpoint decides which files to read.
  • Old files do not count. A new trigger ignores files that were there before. Only files that arrive after you enable it count.
  • Two timers. wait_after_last_change_seconds keeps a multi-file drop together in one run. min_time_between_triggers_seconds is a cooldown. The Jobs API sets a 60-second minimum for both.
  • Development mode pauses each schedule and trigger. The job's own pause_status: UNPAUSED overrides that.
  • No hard-coded IDs. ${resources.pipelines.sanad_medallion.id} gives the correct pipeline for each target.
  • performance_target: STANDARD costs less but starts slower. The pipeline waited 4 min 12 s for compute, then ran for 1 min.
  • No self-trigger. A trigger must never watch a folder that its own job writes to. If it does, the job starts itself again and again.

  • MeI wrote set wait_after_last_change_seconds:20seconds. It had four errors: a stray set, no space after the colon, a unit inside the value, and an extra indent space below. YAML needs key: value, a plain number and equal indentation.
  • MeI chose 20 seconds for both timers, but both have a 60-second minimum. bundle validate accepted 20. Only bundle deploy refused it. Validate checks the shape of the YAML, not the rules of the workspace.

P1.67 Nov

AI/BI dashboard on gold

The bundle deploys sanad_gold.lvdash.json as resources.dashboards.sanad_gold. The one page has 3 KPIs: 2 duplicate invoices, a 2.6% late rate over the year, and 30 VPN tickets on the worst day. Key ideas

  • Three locks. A grant is the door to a table. A row filter decides which rows. A mask decides what a cell shows.
  • The pipeline owns its tables. So you declare masks and filters in the pipeline code (schema="... MASK fn", row_filter="ROW FILTER fn ON (col)"), not with ALTER TABLE.
  • Never filter or mask a table that the pipeline reads later. The pipeline reads as its owner, so the rule would change what it writes. Grants alone protect the PII in bronze.
  • Account groups. UC grants and is_account_group_member() see only account groups. databricks groups create and groups-v2 create made workspace-local groups. workspace-iam-v2 create-group-proxy makes account groups from the workspace.
  • Owner's rights, reader's identity. Filter and mask functions run with the rights of their owner. But current_user() and is_account_group_member() check the reader. So readers need no access to ops.user_regions.
  • An admin gets no exemption. I saw 0 rows until I joined a group. A new membership took about 3.5 minutes to apply.
  • Name clash in SQL. A function parameter with the same name as a column in a subquery loses. u.region = region compares the column with itself. That is why the parameter is row_region.
  • Tags drive the audit. The query finds PII tables through the pii tag, not through a hard-coded list.
  • Audit source. system.access.table_lineage logs one row for each read, under the public table name. system.access.audit logs reads of pipeline tables under internal __materialization_ names and skips reads that use a credential again.

Mistakes

  • MeMy check answer said "it depends on access" but did not say where the leak is. silver.accounts and gold.invoice_issues show all regions. That is why account managers get no silver tables and no invoice_issues.

The basic ideas

Glossary

Each term has one meaning in this guide.

Account group
A group defined at the account level. Unity Catalog grants and is_account_group_member() see only account groups, not workspace-local groups.
ADR
Architecture Decision Record. A short record of context, options, decision and consequences.
Agent Bricks CLI
The agentbricks command that makes, runs and deploys the agent project. It is Beta.
AI Search
The Databricks search service for retrieval (old GA name: Vector Search). It holds an index of embedded chunks.
ai_parse_document
A SQL function that changes a PDF into typed elements: title, section header, text, table.
ai_prep_search
A Beta SQL function that cuts parsed text into retrieval-size chunks and adds metadata.
Answer
The schema of each final reply: answer, citations, confidence and next_action.
Approval (interrupt)
A saved pause before a write tool runs. The same user approves, edits or rejects it, and the graph continues.
Audience filter
A filter on each AI Search query that limits the cards to the departments of the caller. Trusted code sets it.
Auto Loader
A streaming read (cloudFiles) that reads only files that it did not read before.
Bronze, silver, gold
The medallion layers. Bronze: raw data as received. Silver: clean and typed. Gold: business-ready answers.
Bundle
A Declarative Automation Bundle: YAML that declares jobs, pipelines, dashboards, apps and other resources. databricks bundle deploy deploys it.
Change data feed
A Delta table feature that records row changes. Delta Sync reads it to update an index.
Checkpointer
The LangGraph part that saves graph state, for example a paused approval.
Chunk
A search-size piece of a document. It has two faces: chunk_to_embed (what the search matches) and chunk_to_retrieve (what the LLM reads).
Column mask
A function that decides what a cell shows to each reader, for example *** in place of an e-mail address.
Delta Sync index
An AI Search index that follows a Delta table through its change data feed.
Event log
The log of a pipeline, with expectation metrics and planning information.
Expectation
A data-quality rule in a pipeline. It warns, drops the row or fails the update.
Gate
A script with fixed checks and an exit code. Gate A, G2 and G3 are the project gates.
Genie agent
A curated natural-language-to-SQL space over chosen tables (old name: Genie space).
Ground truth
The known right answers. In Sanad, the planted problems and the policy text.
Hybrid search
Meaning search plus keyword (BM25) search, merged by rank (RRF).
Idempotency key
A key that the client sends with a create. The same key gives back the first result, so a retry makes no duplicate.
Inference table
A Unity Catalog table where the gateway logs each model call: request, response, latency and model.
LLM judge
A model that grades the meaning of an answer, for example its correctness or groundedness.
Materialized view
A stored query result that the pipeline keeps equal to its query over all rows (a whiteboard).
MCP
Model Context Protocol. A standard way for an agent to find and call the tools of a server.
Memory store
Facts for each user, kept across conversations (a diary). It is outside Unity Catalog permissions.
MRR
Mean reciprocal rank: the average of 1/rank of the right card. A miss counts as 0.
next_action
A field of the Answer with a closed list of values, for example open_ticket or out_of_scope.
PII
Personally identifiable information, for example names, e-mail addresses and phone numbers.
Prompt alias
A name like @production that points to one prompt version in the Unity Catalog Prompt Registry.
recall@5
The share of questions where the right card is in the top 5 results.
Red team
Test cases that try to make the agent do something unsafe.
Row filter
A function that decides which rows each reader sees.
Runtime store
The state of each request, kept for recovery (a job ticket).
Scorer
A function that grades one trace. It is a code check or an LLM judge.
Service principal
An identity for a program, not a person, for example the identity of an app.
Session store
One conversation, with any paused approval (a whiteboard in a meeting).
Sign test
A test that counts only the cases where two options differ and asks if the split could be chance.
SLA, SLI, SLO
The promise to the customer, the thing that you measure, and the internal target.
Span
One step inside a trace, for example one model call or one tool call.
Streaming table
A table that adds new rows and never reads old rows again (a diary).
Supervisor
The agent that routes each question to specialists and merges their answers.
Trace
The MLflow record of one agent turn: a summary record plus its spans.
TRY_CAST
A cast that gives NULL for a bad value. A plain CAST stops the run in ANSI mode.
UC function tool
A Unity Catalog SQL function with a COMMENT. The agent calls it as a tool.
Unity Catalog
The Databricks governance layer for data, functions, models and permissions.
Unity Gateway model service
A governed wrapper around models: who may call it, routing and fallback, rate limits and an inference table.
